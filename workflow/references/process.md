## 总则3 · 下沉细则

> 总则3 的红线部分(3.1 版本签发 / 3.2 输出物带版本 / 3.3 三条硬约束 / 3.4 双版交付)在 `SKILL.md` §2。
> 本节只装**阶段性动作**才用得到的细则——打包、站点升版、部署上线时才读。

### 总则3.3-细则 · skill 包打包合规

承 `SKILL.md` §2 总则3.3 的三条硬约束,打包时另守:

- **顶层目录名 + zip 文件名带版本号**,用 **ASCII 下划线、不用点号**(如 `guojin-securities-design_v3_19_1/` 与同名 `.zip`),解压后从目录名即可溯源。`validate.py` 已加「目录名缺版本」**P1** 提醒。
- **中文或点号目录名会被拒收**——实例:旧 `国金证券客户端设计系统-skill_v3.17.1/` 不可传,改 `guojin-securities-design/`。
- 打包**排除** `__MACOSX/`、`*.DS_Store`。
- 校验:`validate.py` 已加「非 ASCII 文件名 / 目录名 = **P0**」守卫,产出前自动拦截;版本一致性改读 `VERSION` 文件。
- **本规范不影响自升级**:`check-update.sh` 读 `VERSION` 文件 + 自动定位含 `SKILL.md` 的目录,**不依赖目录名**(见 §4.6)。

### 总则3.5 · 站点(展示站)版本号

站点版本 = **展示站自身独立 semver**,与 DS skill 版本**解耦**、不要求相等(延续「设计系统与工作流版本号各自独立签发」)。

1. **升位 主.次.修**:破坏性改版 / 整站重构 → 主;新增页面或区块、内嵌 skill 包升到新大版本、成规模内容同步 → 次;文案 / 单值 / 局部小修 → 修。
2. **站点各页 / 区块「反映哪个 skill 版本」由【页面内每块版本戳】承载**,**不靠站点版本号表达**——故站点可处 patchwork(不同区块戳不同 skill 版本);**所有区块对齐到某 skill 版本后,方可在文案 / 对账中称「站点已整体对齐 DS vX.Y.Z」**。
3. 站点包内置 `SITE-CHANGELOG.md` 为站点变更**唯一记录**(格式同 skill CHANGELOG);folder 名 + zip 名带站点版本(纯 ASCII,如 `guojin-ds-site-v3_18_0`)。
4. **边界**(延续「展示层只动表现、不反向改真值」):skill 升版**不强制**站点升版(展示层按需同步,同步即按上述升位 + 写 SITE-CHANGELOG);站点升版**绝不反向改 skill 真值**,内嵌 skill 包永远取 skill 已签发版本、不在站点侧二次编辑。
5. **更新与止乱(版本权威 · 防倒挂 · 验回退 · 正名)**:
   - 站点版本号**唯一权威 = `SITE-CHANGELOG.md` 最新条目**;**Design 重生成站点时的 folder 名 / 页眉徽标一律不作版本权威**(Design 常把 folder 标回旧值,如把 v3.19.3+ 内容标成 v3.17.1)——维护方打包时以 SITE-CHANGELOG 为准重标 folder / zip 名。
   - 新版本号**必须 ≥ 现 SITE-CHANGELOG 最新版本**、从「用户保有的真实最新」往后接续,**严禁拿 Design 重生成输出的(可能被标回旧值的)folder 名当基准 +1**(否则「新包版本号 < 已有版本号」倒挂)。
   - Design 从源重生成后,维护方打包前**先与上一基线逐文件比对**(diff 分类:本轮同步项 vs ★其它),确认除本轮同步项外**无内容回退**方可续版;有回退则以基线为准重做。
   - Design 输出 folder / 徽标与真实内容版本不符时,以真实内容续接版本线、在 SITE-CHANGELOG 记「正名」,**不沿用误标**。

### 总则3.6 · 可视化站部署交付规范

Design 交付可上线的部署夹时,以下为**唯一权威**;§4.5 的操作步骤直接引用本节,不重述。

1. **页面文件名一律 ASCII**:首页=`index.html`、基础规范=`foundation.html`、通用组件=`components.html`、业务场景=`scenarios.html`、指南=`tutorial.html`。
2. **`index.html` 在最外层。**
3. **链接全量同步**:首页卡 / nav-data / 面包屑 / ⌘K / 页间互链 / Skill 下载按钮 `href`+`download`,旧名改新名,**交付前 grep 零残留**。
4. **`assets/` 资源也 ASCII**(如 `guojin-ds-skill-v3.2.1.zip`),下载按钮链接同步。
5. **🚧 红线**:部署层**只动文件名与链接**;页面渲染 / 交互、token 数值、750 示例、壳层逻辑**一律不变**。
6. **维护方机械注入时同样守此规范。**

## §3 主流程:标准循环(每个组件 / 每个维度一轮)

```
① 用户:发 Figma 节点链接给 Chat(主路径;截图仅作视觉补充或 MCP 不可用时备用)
② Chat:经 Figma MCP 直读真值与变量绑定(4.1)→ 输出前自检(见 §6)→ 列「已读到 / ⚠️待确认」
       ├─ 有待确认 → 用户拍板规则/命名,不出图(确认前置,非正式确认)
       └─ 无待确认 → 进 ③
③ 【效果确认】渲染校验图(默认 inline 可视化;需留档/离线则出自包含 HTML)→ 用户确认「数值与效果」→ 反复改到"对了"
       └─ 效果确认未过 → 不写进 skill
④ 写 skill:按标准结构重写表述(5.3)写进 skill(md/css)→ 反推自检(自检6)
⑤ 【文本确认】把固化文本给用户抽查「表述与归属」→ 过了才进 ⑥
⑥ 打包/升版本:Code 校验 + 打包 skill(单文件基础规范按需)+ CHANGELOG 升版本 + 回写看板 ✅(文本确认未过不得做本步)
⑦ 同步:Chat 出「只含定稿差异」的 Design 提示词(能给参考实现文件就给文件,5.4)→ 用户粘/传给 Design → Design 更新可视化站
⑧ 取证:Design 导出回传 → Chat 先核版本戳 → 对账取证(4.3)→ 偏差回修
⑨ 发布:站点成熟后整理部署包上线(4.5);日常迭代回到 ①
```

- **校验图交付形态**:默认 **inline 可视化(widget)** 做日常快速校验;**需留档 / 离线 / 像素级自检时,产出自包含可下载 HTML**。两种都要求自包含、可交互、用真实数值。
- **取值路径**:默认走 4.1(Chat Figma MCP 直读);直读未覆盖处(如 SVG 内封装值)标 ⚠️,需要时辅以截图对照;源规范本身不完整则插入 4.2。
- **两次确认**:见 `SKILL.md` §2 总则4——效果确认过才写 skill;文本确认过才打包 / 升版本 / 回写看板 ✅。待确认拍板是确认前置,不替代两次确认。

## §4 子流程(按触发条件插入主流程)

### 4.1 样式提取(Chat 经 Figma MCP 直读;触发:需要 Figma 真实数值)

```
① 用户:把 Figma 节点链接(含 node-id)发给 Chat
② Chat 直读:get_metadata(结构/节点ID)→ get_design_context(尺寸/布局/截图)→ get_variable_defs(颜色/语义 token 绑定)
③ Chat:裁决(**默认以 Figma 直读为准;skill 与直读不符即改 skill**——总则1)→ 赋予语义与规则 → 固化进 skill
④ Code:用固化值渲染校验图,与设计对照 → 改到像
```

**实测准入(铁律)**

1. **只有 Figma 直读值可入库**;读不到的(如封装在 SVG 内的圆角)标 ⚠ 未暴露,**不推导、不脑补**。
2. **变量绑定优先**:`get_variable_defs` 的语义 token 绑定(如 轨道关=H3、滑块=CT6)直接采信,免去 hex 撞库;源稿手写标注与变量绑定矛盾时以**变量绑定**为准。
3. **节点映射 Chat 自取**:源文件迁移后用 `get_metadata` 重新取节点 ID,不依赖历史 ID。
4. **完整性**:提取前先在 skill 找己方既有真值避免重复;多变体逐个读全,缺项显式标注。
5. **越界仍归 Chat**:直读只给「长什么样」;何时用、叫什么、什么语义 / 规则由 Chat 产出;skill 未覆盖的新信息列「待确认」,经用户确认才固化。
6. **🚧 字体替换硬规则**:直读 / 设计稿中出现 **DIN 系字体**(D-DIN / D-DIN-PRO / DIN Alternate 等)**一律改用 GJType**(国金自有数字字体)入库与同步——固化、校验图标注、回写 Figma 时都换;**仅换字族,字号 / 字重 / 行高不变**。(C 端数字字体统一 GJType。)
7. **🚧 图标优先用库(制作原型 / 预览硬规则)**:做原型 / 校验图 / 预览时图标**必须优先调 skill 图标库**(`assets/icons/`:通用→`common/`、场景→`{场景}/`)的真实图标。库里没有的:① 已有上传资产能补的先补入库再用;② 取不到 Figma 资产字节时需用户**导出 SVG 上传**补入库后用;③ 暂不可得则**显式标「⏳图标待补」征求用户**。库内确实没有的可手画占位(标「⏳占位,待替换」)。要点:**先查库、库里有就必须用库里的**,别在库已有时自创画法。

**校验图 =「按真值重建」+ 资产嵌入限制**:校验图按直读真值重建(尺寸 / 色值 / 布局 / 几何),**不是嵌入 Figma 原始资产**。本环境取不到 figma 资产字节(网络白名单不含 figma.com、沙箱不能加载 figma 外链),故**资产级矢量**(精确路径、内封圆角等)只能贴近重建并标 ⚠️;**需像素级 1:1 时走「用户导出 PNG/SVG 上传」**用真实资产再核(`get_screenshot` 的 base64 仅供 Chat 自检,不能直接嵌进交付物)。**重建 ≠ 原始像素须对用户讲明,不蒙。**

**不制造无谓询问**:Figma 已有明确样式的**先直读确认、以直读为准**。**仅两种情况才找用户:① 相比原方案 / 直读,确有更优替代;② 原方案 / 直读样式本身有问题。** 除此不发问;尤其**不拿自己都认为差的方案去问**(假选项凑数)。本该自己直读就能定的不变成提问。

**备用通道(trae)**:仅 Figma MCP 不可用时回退,按旧纪律(回传 md、A/B/C 格式、推导拒收、撞库比对);MCP 恢复后以直读复核为准。

### 4.2 源规范完善流程(触发:Figma/Design 源规范不完整)

源规范不一定完整(「????」占位、缺态、缺数值、不成体系)。此时不是"忠实搬运",而是 **Chat 主动完善**:

1. **取值优先级**:Figma MCP 直读优先(4.1)→ 不可用时截图 / 纯文字 → 仍不行回退 trae。
2. **不完整 = Chat 补全**:补缺态、系统化命名、定规则、补缺数值,而非纯搬运。
3. **忽略占位**:Figma 中「????」等占位文案一律忽略,不当内容。
4. **不确定就问**:拿不准的【规则】(用途、选用条件、命名、缺态)先问用户拍板;仅【像素级数值】可按既有规律给默认值,但须标「⚠️待确认 / 待提真值」。
5. **完善后仍走标准循环**:固化 → 校验图 → 用户确认 → 同步 Design;未确认不写完成、不升进度。

### 4.3 对账循环(触发:Design 自行产出过内容、隔了几轮没同步、或视觉对不上)

> **A 之前先核版本戳**:对账第一步先看 Design 产物的版本号——**若 Design 版本 < 当前 skill 版本,即版本滞后、不是新 bug**;差异多半是"Design 还没拿到最新修复",应先让 Design 升到当前版再对,**别把滞后当问题重新诊断、重新出提示词**。版本一致后才进逐项 diff。

```
A 用户:Design 导出(html/zip)→ 拖进 Chat
B Code:解析并与当前 skill 逐项 diff → 输出【差异表】(项目 | skill值 | Design值 | 判定)
C 裁决:**skill 是站的上游**——默认 skill 对、Design 改;仅当 Design 更合理时标出问用户后反向更新 skill。(**注意:这一层说的是 skill ↔ 站;skill ↔ Figma 那一层以 Figma 为准**,见总则2)
D Chat:据差异生成同步提示词,每条注明「当前写错/缺失什么 → 应改成什么」,不只给目标值
E 用户:粘给 Design → 修正
```

> **对账须核到「资产级」**:B 的逐项 diff 不止比版式 / 数值,还要逐个核**用的是不是 skill 指定的确切资产**(图标文件名、token、参考实现)——版式像、但图标用了占位 / ≡、token 硬编码,都判**不通过**;资产不符**不得提前标「可验收 / 通过」**。
> 日常只走标准循环(先改 skill 再同步)就不漂移;对账是补救与校验手段。

**Design 回报形态规范**:Chat 发起进度对齐 / 盘点时,Design 回报须是**可直接复制的文案**(整段进复制框);**过长时整理成 `.md` 文档交回**,不以零散聊天长文本作对齐依据。盘点须:① 按批次标「本会话已做 / 既有未动 / 未做」;② 附偏差申报;③ 导出现状供 Chat 取证。

**多页站导出**:可视化站是多页结构,**不存在「全站单文件」**;按页 / 分册各自导出,Chat 按页取证;Code diff 以「本轮改动文件清单」为准。

> 站点版本戳的「应为哪版」不在本包裁——查包外《站点版本戳维护表》,并以其为差异表基准逐项核,**戳不符即判不通过**。

### 4.4 图标资产管理(触发:图标随组件出现)

图标按"能否被字体承载"分两类(详见 skill 的 `assets/icons/ICONS.md`):

```
通用单色图标(返回/搜索/设置/分享…) → IconFont 字体(assets/icons/fonts/),<i class="iconfont icon-xxx">
渐变/特效图标(如底部导航选中态)   → SVG(assets/icons/bottom-nav/ 或 gradient/)
复杂动画图标(Lottie/逐帧)          → skill 只写引用说明,资源放外部
```

**判断**:纯单色无动效 → 字体;带渐变 / 特效 / 动画 → SVG/Lottie;**字体绝不能承载渐变与动画**。
**来源与传输**(Code 无外网):iconfont 字体由用户在 iconfont 平台生成后提供(或从 Design 产出 HTML 提取内嵌);渐变 / 动画 SVG 由用户从 Figma 导出提供。Chat 负责还原 + 生成 css + 登记 ICONS.md + 升版本。

### 4.5 发布 / 部署上线(触发:可视化站取证通过、需要线上可访问)

```
① 取一份取证通过的自包含多页站(每页已内联,离线可开)
② 按【总则3.6】做文件名 ASCII 化与链接全量同步          ← 规范在总则3.6,本步不重述
③ grep 复核:旧中文文件名 + 旧 zip 名残留 = 0;Skill 包 PK 头有效、可下载、与权威包 md5 一致
④ 打部署包:最外层直接是 index.html + 英文页 + assets/ + 供下载 zip(Netlify 拖拽即用)
⑤ 上传上线;站内「下载 Skill 包」即下载维护方签发的权威 skill 包
⑥ 本地交付件归档                                        ← 规则见下方「本地文件归档」,本步不重述
```

**🚧 红线**:发布 / 部署**只动文件名与链接**;页面渲染 / 交互、token 数值、750 示例、壳层逻辑一律不变(总则3.6-5)。

**部署前固定核验项(主线-大脑)**:用户提出部署时,大脑**必须先核**站内「下载 Skill 包」与「当前 DS」文案是否为当前权威版本,把差异摆给用户,由用户决定同批刷还是明知故留。位置与处数见包外《站点版本戳维护表》§4,本处不重抄。
**部署时机由用户主动提出**,大脑不主动提议、不催。

**维护方(Chat)亦可执行**:注入 skill 下载包、改部署结构、ASCII 改名等机械操作 Chat 可直接代做(有源文件时),同守总则3.6 并做 ③ 取证。

**站内下载包更新时机**:站内「下载 Skill 包」**在发布 / 部署阶段统一更新到当版**(机械注入或随新部署包替换),**不在组件级 Design 提示词里反复要求**(见 5.4-10)。

**本地文件归档**:发布 / 打包收尾时,各版本线只在原位保留最新交付件,旧版本移入 `历史文件/`。由【主线-手】执行,判定与处置规则(规律明确才处理、拿不准标 ⚠️ 报回)见 `execution-standard.md` §八,本处不重抄。该规则只管维护工作区整洁,**不影响** skill 包内部版本、站点下载区版本、自升级机制或历史 CHANGELOG。

### 4.6 自升级机制维护(触发:改动可能影响 skill 自动更新)

设计系统 skill 自 DS v3.9.1 起带「自升级自检」:使用者启动 skill 自动比对版本、落后则从 Design 站拉新包覆盖安装。机制由四处耦合构成——

- `scripts/check-update.sh`:抓站点 `index.html` → 从下载按钮 href 的 `guojin-ds-skill-vX.Y.Z.zip` 解析远端版本 → `sort -V` 比对本地 `VERSION` → 落后则下载覆盖安装;**失败永不阻断**(任一异常都 `exit 0` 放行)。
- `VERSION` 文件:本地版本号,**须与 SKILL.md `version` 一致**。
- `SKILL.md`「第 0 步:升级自检」:启动即跑。
- 站点侧约定:发版后把新 zip 部署到 `assets/guojin-ds-skill-vX.Y.Z.zip`(ASCII 命名、版本在文件名),且**站点版本 ≥ 本地方触发更新**。

**🚧 硬性要求(不可降级,见 `SKILL.md` §1 总则0①):任何可能影响自升级功能的改动,必须事先「重点 · 显式」向用户说明影响面、取得确认后才动,不得静默改。** 涵盖:`check-update.sh` 逻辑(版本解析正则 / 比较方式 / 下载覆盖放行分支 / 代理 / 超时 / 顶层目录定位)、`VERSION` 文件存废与语义、`SKILL.md`「第 0 步」存废或行为、**站点下载区 zip 命名 / 路径 / 版本文案**(脚本据此解析)、部署命名约定与站点↔本地版本对应关系。
常规组件 / token 改动不受本条约束(但其版本号变化仍照总则3)。

### 4.7 Figma 组件同步落地(写操作;触发:把已固化真值反向建 / 改 Figma 组件)

把 skill 真值写回 Figma 库(`use_figma` 经 Plugin API)。**写操作有成本、不可逆,前置纪律从严:**

**前置(每次必做)**
- **成本意识**:`use_figma` 写操作消耗较多点数。能用 skill 真值 + 校验图表达的优先用;**Figma 绘制按需、且必经用户显式"可以"才动手**(写操作属两次确认外的额外闸门)。
- **加载技能**:动手前必加载 `figma-use`(API 规则)+ `figma-generate-library`(建组件流程);调 `use_figma` 时 `skillNames` 传 `"figma-use,figma-generate-library"`。
- **保留原内容**:同步默认**新建组件、不原地改原件**。

**字体配方(本环境关键坑)**
- 本环境 **PingFang SC / GJType 等不能直接 `loadFontAsync`**;可加载实测:Inter / Roboto / Noto Sans SC / Noto Sans ✓,Arial ✗。
- **配方**:① 用 **Noto Sans SC** 打底 `createText` → ② **先把 `fontSize`/`lineHeight` 定到目标值** → ③ 再 `await t.setTextStyleIdAsync(样式ID)` 套库内文本样式换字族(中文 `S8-CN-R`=PingFang 20/30、数字 `S7-NUM-M`=GJType Medium 24/36)。
- **反例**:不预定字号直接 `createText`(默认 12px)→ 套样式 → 重排需加载 PingFang 而加载不了 → **静默失败**,字形停在 ~12px,样式面板仍显 20/30(标签对、字形小)。
- 承 4.1#6:见 DIN 一律改 GJType;涨跌幅符号统一 GJType。

**布局 / 高度**
- missing-font 会让 auto-layout 文本盒按字形收缩 → **组件高度显式锁**:`counterAxisSizingMode='FIXED'` + `resize(w, 目标高)`。
- **不能原地改 unloaded-font 文本**:改字号 / 字族会 throw `unloaded font` → **要改就删了重建**。

**变量绑定**:`getVariableByIdAsync(id)` → `figma.variables.setBoundVariableForPaint(paint,'color',v)`(返回新 paint,回写 `node.fills`/`strokes`)。按变量**叶名**匹配定位 ID(如 `CP0`/`CL3`/`CB13`)。底 / 字 / 描边都绑;无对应变量的才用 raw + opacity。

**建组件流程(小步 + 校验 + 确认)**
1. 只读探查:页面 ID、放置空位、所需颜色变量 ID、字体可加载性、文本样式 ID。
2. **先小范围试做一个** → `get_design_context` 截图核实 → 用户确认"第一次效果"。
3. 确认后再建其余;每建一个截图核一次。
4. `combineAsVariants` 后变体堆叠在 (0,0),需手动栅格 / 换行(`layoutWrap='WRAP'` + 固定宽);二维属性用变体名 `属性A=值, 属性B=值`。
5. 组件 `description` 填一句使用说明。

**API 纪律(figma-use 铁律)**:颜色 0–1 区间;`fills`/`strokes` 只读数组,克隆改回写;**每个 Promise 必 `await`**;**page context 每次重置**(脚本开头 `await figma.setCurrentPageAsync(page)`,一脚本至多切一次页);**绝不并行 `use_figma`**(状态变更须串行);脚本出错是原子的——读错误、改对再重试,不盲目重试;**返回所有 created/mutated node ID**,不臆造。

### 4.8 生成页面的可靠性三层(触发:用 skill 出任何页面 / 原型)

把"使用者能生成符合规范的页面"从「靠模型自觉」改为「靠机制」。规则写进文档 ≠ 模型执行时会查库,故三层缺一不可:

1. **降摩擦(第一层)**:一切可复用资产登记在 `assets/library-index.json`(图标 / 组件 / token → 库内确切引用),配 `icon-palette.html`;资产变动后重跑 `scripts/build-index.py`。让"照抄库内引用"比"手画 / 重写"省事。
2. **强制产出 BOM(第二层·闸门 A)**:动手前先出《用料清单》表——每个图标 / 组件 / token 写明库内引用,查不到才标 ⏳。**BOM 填不出 = 没查库。** 反复嵌套复用的组件一律指参考实现、不就地重写。
3. **确定性校验(第三层·闸门 B)**:交付前必跑 `scripts/check-page.py 页面.html`,**P0=0 才准交付**,P1 逐条复核。模型会忘,脚本不会。

**铁律**:闸门 A、B **不可跳过**;影响三层的改动(索引结构 / 生成器 / 校验规则 / 闸门文案)按 4.6 同级,经用户重点确认。

## §5 产出标准(各类交付物"做成什么样"才合格)

### 5.1 组件抽象与复用

- **通用 vs 专属分清**:通用组件规格写成"可配置"(如底部导航 tab 数与图标可替换、建议 ≤5),示意图标标"仅示意"且用专用图标集 active+inactive 配对;专属变体单独成组件,不混入通用;拿不准问用户。
- **复用优先,旧组件必须嵌套**:新组件若含已有组件的样式 / 结构(按钮、图标、tab、标签、分割线、胶囊等),**必须以「实例嵌套」复用**,不重画 / 复制样式另起一份;固化时写明"由 XX、YY 既有组件嵌套组成",不把子组件尺寸色值再抄一遍。是否等同已有组件、该不该复用,**先与用户确认**。好处:改底层,上层自动跟随。
- **交互以文字规范沉淀**:交互行为(点击切换、滚动响应)写进 skill 作文字规则;是否做可点击 demo **按用户要求**,不擅自加用户没要的交互演示。

### 5.1b 参考实现:组件本体 vs 演示外壳,以及「这份文件服务谁」

**参考实现 HTML 里有两种东西,先分清再动手**:

| | **组件本体** | **演示外壳** |
|---|---|---|
| 指什么 | 被固化的那个组件自身 | 标题、说明、规格卡、排版网格、主题切换、交互控件、来源说明 |
| 真值来源 | **Figma 直读**(总则1);无设计图时按规范近似值 | **一律用规范值**(token),不另立数值 |
| 改动要求 | 任何改动都要做回归比对(§6 自检5) | 同样要 token 化 / 规范化 |
| 尺寸变化 | 算回归,要解释 | **不算问题** |
| 上不上站 | **上**(Design 同步的就是它) | **不上站** |

**⛔ 生成前先定「这份 HTML 主要服务谁」,默认只选一个主用途**:**参考实现**(默认,一个主预览 + 必要变体,**不自动展开成完整测试矩阵**)/ **效果确认页**(给用户拍板,看完即弃)/ **测试页**(覆盖边界异常,内部用)。

- **每个可视模块要回答一个独立问题**;主预览已能表达的,不再复制一组状态卡片(§7.1 载体对照表)。
- **变体与边界优先写进实现规则与自检,不默认做成展示模块**;要留的信息放进 DOM / CSS / BOM 与简短说明。
- **借别的组件只借组织结构,不继承它的视觉布局**——视觉真值只认 Figma 与该组件自己的规格(总则1)。
- **实证**:C09 进度条第一版把参考实现、人工效果确认、内部测试矩阵三种用途做进同一份 HTML,组件本身没有交互却出现了「交互试验台」标题,页面更像测试报告。

### 5.2 校验图(1:1 还原方法论)

1. **真实 iconfont 字体**:通用图标用还原的 woff2 + `<i class="iconfont icon-xxx">`,不用 emoji / 手画凑;**渲染截图前等字体加载完**。
2. **Figma 绝对值布局**:尺寸 / 间距 / 字号直接用提取的 750 实测值,不靠"大概比例"。
3. **真实状态栏组件**:复用 `assets/components/status-bar.html`;wifi 扇形画不准就用 "5G" 文字替代。
4. **自适应 flex,不写死宽度**:容器 `width:100%`、操作栏 `flex space-between`、左右组 hug——对应 Figma 的 fill/hug。
5. **渐变 / 特效图标用内联 SVG / img**:从 skill 资源读 SVG;示意图标用专用图标集 active+inactive 配对,不用无关字体图标顶替。
6. **可交互组件一份 HTML 两用**:可交互组件的效果确认**以 HTML 做一份**,过确认后直接沉淀为该组件参考实现(`assets/components/xxx.html`),不另造静态校验图;简单 / 非交互组件用 inline 可视化快速确认。

> 复杂图标(如微信 capsule 内靶心、关闭 ⊗)手画易错,精度不够时走 4.1 要精确参数,**不硬猜**。

### 5.3 固化文本(校验图文案 ≠ skill 文案)

校验图标注是**校对速记**(允许混排、缩写、口语),不是规范文本。固化进 skill 时:

1. **必须按标准结构重写**:组件定位(是什么 / 用在哪)→ 构成与嵌套 → 变体与参数表(档位 / 字号 / 颜色,引用 token)→ 行为规则(交互 / 滚动 / 选中态,与静态样式分开)→ 备注(源稿差异与裁决)。**不照搬校验图文案。**
2. **规则归属分明**:不同组件规则分开写、不混述;一条规则只写在它所属组件下。
3. **用户只确认两次**:校验图一次(数值与效果)、skill 文本一次(表述与归属,可抽查)。

### 5.4 Design 提示词

> 复制框骨架 → `assets/templates/design-prompt.md`,**照抄,不自创**。

1. **主交付物 = 参考实现文件本身,不是 prose 重述**:固化组件 / 场景给 Design 时,**首选直接交付该组件的参考实现文件(HTML/CSS/SVG)+「1:1 照此渲染:图标 / 资产一律用文件内的、禁自画 / 内联近似 / 自行简化」**;prose 复制框退为"差异说明 + 归属 + 版本",不充当 Design 重新理解重画的唯一依据。原因:参考实现是像素级正确的唯一真源,Design 吃 prose 重画 = 每个表述缝放大成一整轮。**能给文件就别让它重画。**
2. **从 skill 生成**:对外同步表述一律以 skill 固化后文本为源,不从校验图复制。
3. **只含定稿表述**:全部是已确认的最终规范,用规范口吻陈述;不出现「决议 / 待确认 / 源稿已废 / 讨论过程」等过程性表述(纠错指向除外,且只说"应为什么"不说"为什么改")。未决项先问用户拍板,拍板前不进提示词。
4. **写差异 + 纠错指向**:只写差异、不让整页重做;每条注明「当前写错 / 缺了什么 → 应改成什么」,给规则与意图,措辞清晰简洁。
5. **定位用站点实际页面名**:每条提示词显式注明更新位置(哪个页面 / 哪个章节区块);Design 不得新开页面,除非明确写「新开页面」。**新固化的业务组件 / 场景须用 Design 站【实际页面名】指明归属业务页**(对账时已知站点结构,如行情→`scene-quote.html`),并写明"作为该页新增区块加入(非新开页面)";**不用逻辑名(如「自选页」)虚指。**
6. **全站可稳定预览 + 导出件自包含**:所有页面在制作全程任何时候打开都不报「未发现文件」/ 空白。**根治机制**:交付 / 导出的每个 HTML 页面必须**自包含、零外部依赖**——把共享 shell 的 CSS/JS、nav-data 在导出时**内联进每页**,不残留指向未随包文件的 link/script。Design 内部作者态可保留单点真源,但**导出动作必须内联**。此为常驻要求,不必每轮在提示词重复。
7. **明暗双版组件的展示方式**:带白 / 黑版(浅 / 深双版)的组件,在站里**展示须跟随网页明暗主题切换**(白肤显白版、黑肤同处切黑版),**不在同一主题下并列静态铺两版**。组件底色真值不变,这里约束的是"展示哪一版"。
8. **开头注明版本号**;按 `SKILL.md` §2 总则6 以复制框交付。
9. **复制框执行回执**:每发出一份 Design 复制框后,发下一份前**必须先问用户上一份的执行 / 落地情况**(是否做完、是否需先对账),确认后再发新的。
10. **不夹带下载包升级**:组件级提示词只描述"该组件 / 页面在站点的还原",**不夹带站内下载 skill 包的升级要求**(那属发布 / 部署阶段统一更新,见 4.5)。
11. **不默认要求 Design 导出**:组件级 / 区块级提示词**不附「做完请导出」**——整站导出耗用户点数,改完让 Design 回一句确认即可。**仅两种情况明确索取一次导出**:① 需对账取证(4.3);② 打包 / 部署前(4.5)。同一份导出可兼作两用,**不重复索取**。
12. **不写未确认的他方执行状态**:正文只列本份**已确认定稿的当版差异**;不夹带"若上一批某项未完成则继续 / 补做"之类未确认 carry-over(靠第 9 条口头跟踪)。

## §6 输出前自检(Chat 每次给用户内容前必做,不可跳过)

**任何交付物(预览 / 规格 / 提示词 / 文件)发给用户前,先过这份自检,确认无误才发。**

0. **源数据全量比对(最高优先,先于一切)**:交付物中每一处数值 / 属性 / 状态,逐项对照已提取真值与用户决议核一遍;**凡某轮出现修改,即说明存在偏差,必须触发整体重新匹配**(不是只改被指出那处);真值未覆盖或含义不明处列清单问用户。
1. **精确读取**:数据逐处读准(必要时放大、用 Code 提取),不靠记忆;读不准标 ⚠️,不蒙混。
2. **常识校验**:对照参考或自行推理,矛盾或不确定先问用户,不擅自定。
3. **一致性校验**:token 是否存在、白黑版是否成对、字号↔S编号↔token 对应、与已固化内容是否冲突。
4. **自我覆盖检查**:多处编辑同一文件后,确认没把已有内容意外删除 / 覆盖。
5. **渲染确认(视觉比对,不只看一眼)**:渲染校验图后自己 view 并**逐项比对**——背景 / 白底、边框、圆角、元素齐全、颜色、无透底 / 错位 / 缺失。**自适应宽组件必须放在"宽于内容"的容器里渲染**,否则"等分填充 vs 写死宽 / 左对齐留白"看不出。走 inline 可视化拿不回渲染像素时,自检5 以"代码级逐项核对数值 / 色值 / 状态"为准;需像素级时产出 HTML 由 Chat view 后逐项比对。
   > **⛔ 批量替换类改动(改 token 名、换写法、引用 token 化)光看图不够**,必须做**改前 / 改后计算样式的逐元素比对**(颜色、圆角、间距、位置;浅色暗色各跑一遍),**0 差异、或差异逐条能解释**,才算通过。
   > **为什么**:这类错肉眼看不出、脚本也不报。**实证**:DS v4.0.0 把 SP/RD 定义写进了 `bottom-nav.html` 的**文件头注释**里,页面引用的 `--SP*` 全部没有定义、按 0 计算,高度从 1153 缩到 951;此后 v4.0.1–v4.1.0 跑 `validate.py` 都是 0 P0,**连四版没被发现**,直到 v4.1.1 做比对才查出。`sandbox-header.html` 少 5 个 token 副本、`var(--RD8)` 算成 0px,同样是比对才发现的。
   > 反过来,v4.0.2 / v4.1.1 两版正是用这个方法当轮抓出了 `clamp(0,…)` 失效这种看不出来的错。
6. **反推自检(语义自足)**:写完 skill,**只读刚写的规则文字、不看参考实现**,自问"能否唯一重画出合规效果?"——画不出或会发散(资产没钉到该层精度、自适应 / 状态没说清),即规则有洞,补到自足再收口。**组件 / 场景首次固化前,反推审走【整条规则、不只改动处】**——一次把潜在缝挖干净,别哪痛医哪、分多轮挤。并同时做**内部自洽核**:参考实现 ↔ prose ↔ token/资产 三方逐项对一遍,防自埋矛盾。
7. **回归检查**:在已有版本上改动后,对照上一版确认**只改了该改的、没弄丢已确认的**;改 A 不悄悄破坏 B。
8. **版本标注**:**已签发**的交付物带当前版本号;**预览 / 草稿带轮次号 `r{n}`、不带资产版本号**(总则3.2);预览标清「已读到 / ⚠️待确认」。
9. **交付节制(治过度交付 / 浪费用户点数)**:present 前**逐个过每个文件,只发用户此刻真正需要的**(决策项 / 效果确认图〔若需〕/ 最终交付物)。
   - **内部自检产物不发**:核对齐 / 色值 / 数值用的渲染图、量算、中间件是验证手段,**默认不 present**。
   - **渲染图只在「用户须看效果拍板」时才发**,且**数据要真实有代表性、能据以判断**;劣质 / 重复假数据的图不发。
   - **发了不许自我否定**:不得 present 一张图又说"这图不重要 / 看文件吧"。要么给能确认的,要么不发。
   - **每个交付件标明用途**(给用户确认 / 给 Design 用 / 留档)。

**强制执行**:每条在每次 present 前实际走一遍,尤其第 5、6、7、9 条针对视觉 / 语义 / 交付。**跳过自检直接让用户确认 = 流程违规。**

## §7 不重复原则与活动件维护

### 7.0 载体按「变更频率」分,不按「主题」分

**同一个载体里,变更最快的那部分决定整体节奏。** 把月级的背景和轮级的工单放一个文件,结果就是这个文件每轮都动。

判据 —— **这条内容多久变一次?**

| 频率 | 载体 | 装什么 |
|---|---|---|
| **阶段 / 月** | 《项目总览》(档案件) | 背景 · 目标 · **阶段与里程碑** · 当前基线(**只版本号**)· 协作指引 · 踩坑 · 已否决 |
| **轮 / 天** | **各线自己持有** | 逐项待办、执行卡状态、组件逐格进度 |
| **随升版** | 各资产自己的 `CHANGELOG.md` / 待补段 | 每版改了什么、内容勘误 |
| **出包当轮** | 《DS 改动核验台账》 | 每个已签发包的校验值与核验状态(见 7.4) |
| **一次性** | 执行卡与反馈 md | 某轮做了什么(过程件,用完即弃) |

> **对《项目总览》尤其要紧**:它是**开窗必带件**,靠快照传播。一个每轮都变的必带件,意味着每个窗口手上的版本都不一样——**WF v6.5 撞号那件事的根因正是这个**,当时只修了计数器,没修「为什么计数器会在那儿」。
> **实证(2026-09-23)**:《项目总览》一天内被改了九次;按本条收敛后**砍掉约三分之一,少掉的全是工单与副本**。

#### 《项目总览》装什么 · 不装什么

《项目总览》是长期迭代的**档案件**,不是工单板,也不是一次性会话记录。它承载项目背景与目标、**当前基线(版本真值唯一位置)**、**阶段与里程碑**、协作指引、历史踩坑、已否决。**不留历史快照**,追溯看各资产自己的变更日志。

**⛔ 以下一律不进《项目总览》**:

- **逐项待办与执行卡状态** —— 归各线自己;本文件最多每条线一行「当前在做什么」,不展开细目。
- **进度看板每格状态**(某组件 📋→⏳→✅)—— 那是工单粒度。里程碑是「参考实现补齐」,不是每个组件走一格。
- **各资产的内容勘误与待补项** —— 归该资产自己(升版测试:改它要升该资产的版 → 就不归这儿)。
- **「已完成」流水** —— **那是各资产 `CHANGELOG.md` 的副本**。实证:2026-09-23 删除该节时实测 35 行里工作流包相关的逐条内容全在包内 `CHANGELOG.md` v6.0–v6.6,**是第三份副本不是唯一来源**。本文件只留一张「想查什么去哪查」的指向表。
- **任何包的字节数 / MD5 / 内容指纹** —— 校验值属于**某一次投递**,写进长期档案只会沉淀出过期值。**它们有专门的归宿:《DS 改动核验台账》(7.4)**。
- **计数器类的值**(如「下一个可用 EXEC 编号」)—— 靠快照传播的东西防不住并发,详见 `SKILL.md` §3.2。

**状态符号**沿用全局标注(✅/⏳/📋/🗂️/⏸️),**不得把未经过对应确认 / 发布条件的事项提前标 ✅**。

#### 活动件的文件名与引用

- **文件名可以带版本号**(如 `国金DS常驻-项目总览_v1.3.md`),**只用来分辨手上是哪一份**,每改一次升一位;版本真值仍只记在该文件自己的「当前基线」一处。
- **⛔ 引用一律写书名**(《项目总览》),**不写版本号、也不写路径**。带版本号意味着**文件名每升一位就变**,写死路径的地方必然失配。
- **不留历史快照**:旧版不归档、不另存,追溯看各资产的 `CHANGELOG.md`。
- > 原先规定「活动件不带版本号」,理由是怕各窗口手上的快照对不上。实测反了:**带上版本号反而一眼看得出谁手上是旧的**(用户 2026-10-22 裁定)。
### 7.1 不重复原则 —— 同一内容只出现一次

> **这是本包的第一性规则,其余各条都是它在某个载体上的具体化。**

**同一条内容,整套里只写一处,别处只留指向。** 重复的代价永远是双份:写的人写一遍、读的人读一遍;而且两处措辞必然反向漂移,漂移之后没人知道该信哪个。

**它跨载体生效,不只管文件与文件之间。** 下面每一对都适用:

| 载体对 | 违反的样子 |
|---|---|
| 《项目总览》↔ 本包 | 踩坑表「改法」栏重抄规则正文 |
| 执行卡 ↔ `execution-standard.md` | 卡里重写 §六 的常规验证项 |
| 转交复制框 ↔ 卡 / 附件 | 框里放一段「要点」,摘要文件里已有的内容 |
| 执行反馈 ↔ 执行卡 | 反馈里重述卡文 |
| 续轮开场白 ↔ 规则文件 | 续轮重抄一遍规则 |
| 资产 `CHANGELOG` ↔ 资产 `references/` | 更新记录里把规则正文整段抄一遍,而不是指向该规则所在章节 |
| 参考实现的展示模块 ↔ 主预览 | 主预览已能覆盖 0–100%,旁边又摆一组边界状态卡片 |
| 主线复读 Figma ↔ 支线已直读的真值 | 支线已直读、效果确认也过了,主线入库前再读一遍同一节点 |

**通用判据就是下面的删除测试**,换个对象用:**把这段话删掉之后,对方照他手上已有的东西做,还能不能做对?能 → 删。**

> ⚠️ **「怕他不看」不是保留副本的理由。** 对方不看指向,是指向写得不够准(没点到文件 + 章号),补准指向;不是再抄一份。

#### 内容归哪边 —— 三条测试

《项目总览》是包外活动件。**某条内容该进本包还是进它,按这三条判,别靠直觉**:

| # | 测试 | 判定 |
|---|---|---|
| **1 · 升版测试** | 改这条内容,**需不需要升本包版本**? | 需要 → 归包;不需要 → 归《项目总览》 |
| **2 · 删除测试** | 把《项目总览》里某句删掉后,**还能靠指向找到完整规则吗**? | 不能 → **包里缺这条规则,该来补包**,不是塞进活动件 |
| **3 · 时序测试** | 用户需要在**打开包之前**知道吗? | 是 → **必须在包外**(如「开窗要带什么」);否 → 归包 |

**三条都过不了就别写。**

> **⚠️ 测试2 是报警器,不是筛子**:活动件里反复出现「有现象、没规则可指」的条目(例如收尾核对连报三轮同一个偏差),那是**包里缺章节**在报警,应当来补包,而不是在活动件里攒。
> **《项目总览》§五 踩坑表的书写纪律**:「改法」栏只写**要点 + 指向本包条号**,不重抄规则正文——抄进去就是第二处副本。
> **活动件不写自己的校验值**:《项目总览》正文里不写它自己的大小 / MD5,写了每改一次就失效;要核它,权威值写在当轮执行卡里。

### 7.2 《项目总览》的 `meta/` 副本 —— 按需同步,不是每改必同步

《项目总览》每轮都动,**不为每次改动出执行卡**。`meta/` 里那份是给**有本地访问的窗口**(授权了工作区的 Cowork 支线)读的,同步时机:

- 要开有本地访问的窗口之前;
- 阶段性收尾(如包升版落地)顺带一起;
- 用户明确要求时。

> 判据:**没人要读它的时候,副本旧着不影响任何人**。主线-大脑与无本地访问的支线拿的是用户当场上传的那份,不经 `meta/`。

### 7.3 其它维护规则

- **进度看板不进本包,也不进《项目总览》**:逐格推进状态是**工单粒度**,归**各线自己持有**(§7.0)。《项目总览》只到**里程碑**粒度。**更新时机**仍受总则4 约束:组件经**文本确认通过**后才算完成,两次确认前 / 之间注明卡在哪一次,不提前标 ✅。

### 7.4 《DS 改动核验台账》—— 第三个包外活动件

| 项 | 内容 |
|---|---|
| **管什么** | 每个**已签发**包的 zip 字节数 / MD5 / **内容指纹** + 本版核验状态 |
| **谁写** | 签发方(主线-大脑,或有文件读写能力的主线窗口),**出包当轮登记** |
| **何时读** | 用户回传 skill 包、需要确认「手上这份是哪一版」时 |
| **⛔ 不装什么** | **改动细节**——那在该资产的 `CHANGELOG.md`,台账只写「见 CHANGELOG vX.Y.Z」 |

**为什么单设一份**:校验值**从包里推不出来**,执行卡用完即弃,而《项目总览》按 7.0 不记校验值。**三者各有不记的理由,所以需要一个专门记的地方。**
**与《项目总览》的分工**:总览记**版本号**,台账记**校验值**,CHANGELOG 记**改动内容**——三处互不重叠。
