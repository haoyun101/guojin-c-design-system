# 多窗口协同 · 谁在哪个窗口干

> **本文件讲**:多角色多进程怎么协同——谁干哪步、开窗带什么、开场怎么说、交回给谁。
> **和 `process.md` 的分界**:那份讲**这件事怎么干**(取值 → 固化 → 展示 → 发布的过程规则),本份讲**谁在哪个窗口干**。过程规则一律在那份,本文件只指步骤号,**不重抄**。
> **性质**:索引,不是副本。同一条规则只在一处;本文件出现的都是那份没有的「开窗专用件」。
> **冲突优先级**:**用户当轮明确指令 > 工作流包 > 个人使用习惯文件**(全包统一一档,包内各文件不再分档)。

---

## §1 铁律与角色

**设计真值在 Figma,skill 一份、版本只签一次。** 只有【主线】能写 skill、签版本;【支线】只读 + 起草,产出「待并入草案」。并行起草、合并串行(git 多分支单 main)。
> 「一份」说的是 **skill 这个执行载体只有一份、只有一个签发方**,不是说 skill 就是设计真值的源头——设计真值在 Figma(`SKILL.md` §2 总则1)。

> **⛔ 本包(WF)的版本由用户指定的单一窗口签发,当前是【工作流窗口】。** 其它窗口发现问题**只提建议、不直接改包、不自行升版**。
> **实证**:2026-09-23 出现 v6.2 与 v6.3 两条基线并存——工作流窗口按自己的线以为基线是 v6.2,而另一个大脑窗口已签发并落地 v6.3,险些把 v6.3 静默回退。
> 这一条与总则3.1「签发以 present 为界」配套:**present 即冻结,而能 present 的只有一个窗口**。DS skill 的版本仍由【主线-大脑】签,两条版本线各有唯一签发方。
> 注:上一句「只有【主线】能写 skill、签版本」写于只有一个大脑窗口的时候,**是按旧角色集写死的枚举句**(同类坑见 §8 第二条)。

**主线内部判断与动手分开**:裁决与签发在【主线-大脑】,文件执行在【主线-手】。手不做业务裁决、不自行判断版本升位。**权仍是一份。**

**两次确认按线分布**(出处:`SKILL.md` §2 总则4):效果确认(数值与效果)在**支线**,过了草案才成立;文本确认(表述与归属)在**主线-大脑**,过了才升版打包。

| 角色 | 载体 | 写 skill | 职责 |
|---|---|---|---|
| **主线-大脑** | Claude Chat(**载体有文件能力时可自己动手**,见 `SKILL.md` §3.3) | 判断 / 签发;文件操作**按载体能力**走 | 拆任务、裁决差异、签版本号、出 Design 提示词、验收 |
| **主线-手** | ChatGPT(挂 `execution-standard.md`) | 只执行大脑指令 | 入库、打包、跑校验脚本、归档、机械检查草案 |
| **支线-组件** | Claude Chat / Cowork / 其他模型 / 同事 | ❌ | 取值 → 效果确认 → 交「待并入草案」 |
| **支线-站点** | Claude Design | ❌ | 消费定稿内容出展示站 |

三条边界补充:

- **支线载体不限形态**——窗口、Cowork、别的模型、真人同事都算支线,边界都是「只读 + 起草,不写库不升版」。
- **Design 是特殊支线**——其它支线交回**草案**(→ 并入 skill);Design 交回**下游产物**(→ 走对账 `process.md` §4.3,**绝不反向改真值**)。两者别混。
- **主线-大脑无本地文件访问**——它对文件的一切读写都经主线-手执行,或由用户上传下载。

## §3 开窗:说什么、带什么

### 3.1 开场白

**这是整套里唯一不是文件的东西**——由用户手打或粘贴。文件不会自己说「先读我」;**没有这段,§3.3 的读取顺序不会被触发**,窗口会直接开干。

模板**照抄,不自创**:

| 角色 | 模板 |
|---|---|
| 主线-大脑 | `assets/templates/kickoff-brain.md` |
| 支线-组件 | `assets/templates/kickoff-branch.md`(含**续轮任务卡**) |
| 主线-手 | 不走开窗流程,规则已挂载常驻;每轮只发 `$guojin-design-system-executor` + `【{本轮编号} · 本轮任务】`,格式见 `assets/templates/exec-card.md` |
| 支线-站点(Design) | 不发开场白,只发已定稿的参考实现文件 + 差异说明复制框(`process.md` §5.4,骨架见 `assets/templates/design-prompt.md`) |

> **续轮不重发开场白**:同一支线窗口做第二个及以后的组件时,只给「本轮组件 / 产出文件 / 规格位置 / 本轮特有约束」四样,**不重抄规则**——重抄一遍就是第二处副本,且两次措辞必有出入(§8)。格式见 `kickoff-branch.md` 下半。

### 3.2 带什么文件

**先判:这个窗口有没有本地访问能力?**

| 窗口类型 | 怎么拿文件 |
|---|---|
| **有本地访问**(挂了执行端 skill 的 ChatGPT、授权了工作区的 Cowork) | 直接读工作区;开窗只告知角色 + 授权范围,不必逐份上传。授权按 `workspace.md` 权限矩阵配——支线只给自己那个 `drafts/{支线}/` 读写 + `skill/` 只读 |
| **无本地访问**(Claude Chat) | 用户上传,按下表打包 |

> **各角色具体带哪几件 → 见《项目总览》§三「开窗要带什么」,那里是权威。**
> 理由(时序测试,`process.md` §7.1):用户必须在**打开本包之前**就知道要带什么,所以那张表只能在包外。本节只管上面这条「有无本地访问」的取法差异。

> **带 zip ≠ 开窗就读全。**
> **支线要瘦装时**,DS skill 侧至少给:`SKILL.md` + `assets/library-index.json` + `references/foundations.md` + `assets/design-tokens.css` + 该组件相关 `references/components.md` 段 + `assets/icons/icon-palette.html`。

### 3.3 读取顺序与按需纪律

**必读(全读,按序)**:① 本工作流的 `SKILL.md`(操作卡 + 总则 + 角色通道 + 路由表)→ ② DS skill 的 `SKILL.md` **入口**(只读版本、三层路由、硬规则,它是后面按需读取的导航)。

> **两个必读都是入口,不是全文**。本包的 `references/` 与 DS skill 的分层内容一律**触发才读**,路由见 `SKILL.md` §4。
> **用户个人使用习惯文件不在本序列**(见 §3.4):该文件(如有)由载体自动加载,**不必上传、不必列进读取顺序**。窗口若没有它,按本包执行即可。

**按需(触发才读)**:

- 做 / 核某组件 → 经 DS `SKILL.md` 路由读 `references/components.md`(通用)或 `references/scenarios/{场景}.md`(业务)**对应段** + 该组件参考实现
- 用图标 / token / 资产 → 查 `library-index.json` 定位确切引用,再读那个文件
- 对账 / 发布 → 才读设计站**相关页**(先核版本戳,`process.md` §4.3)
- 配授权 / 归档整理 → 才读 `workspace.md`
- 这轮只碰行情,就不读交易 / 理财场景段

> **按需读取不是偷懒,是纪律**:省的是用不上的预读;真用到的段必须经 `SKILL.md` / `library-index` 定位读准(守总则1),**不靠记忆脑补**。

### 3.4 这套东西有哪几份

**本工作流 skill 包(一份,随窗口附给大脑与支线)**

| 文件 | 作用 | 谁必读 |
|---|---|---|
| `SKILL.md` | 主路由 · 唯一红线权威(操作卡 + 总则0 + 七律 + 角色通道 + 路由表) | 大脑 + 支线,**入口必读** |

**包外(不随包升版)**

| 文件 | 作用 | 谁必读 |
|---|---|---|

| 《项目总览》 | **当前基线(版本真值唯一位置)** + 阶段与里程碑 + 踩坑 + 已否决(**档案件**) | 🔻 各窗口通读 |
| 《站点版本戳维护表》 | 站点所有版本号的单一真值表(**活数据表**) | 🔻 仅站点同步 / 对账时 |
| 《DS 改动核验台账》 | 已签发包的校验值与核验状态 | 🔻 要确认手上是哪一版时 |
| DS skill 的 `SKILL.md` + 分层内容 | 设计系统真值(**操作对象**,非规则) | 入口必读,内容按需 |
| 可视化站 | 对外橱窗(**非事实源**)¹ | 🔻 仅对账 / 发布 |

> **各资产当前版本号一律查《项目总览》「当前基线」**——本包**不复制其它资产的版本号**(本包自己的版本在 `VERSION` / `metadata.version` / `CHANGELOG`,那是它的签发源,不在此列)。原因:同一信息写两处必反向漂移;并入前《多窗口协同工作流》的「当前版本」栏正是实证——自定稿起从未被更新,支线开窗时读到的版本与随包实物不符。
> ¹ https://gjzqdesign.netlify.app;站内「下载 Skill 包」= 维护方签发的权威包。

> **包外活动件怎么命名**:`{层}{使用场景}-{书名}_{版本}.md`。
> **层** = **通用**(跨项目,可直接搬走)/ **国金DS**(本项目专有)。
> **使用场景** = **常驻**(每窗口都要,按需读不预读)/ **按需**(触发才带)。
> **版本**:活动件的**文件名可以带版本号**,只用来分辨手上是哪一份,每改一次升一位。**引用一律写书名、不写版本号、也不写路径**——文件名每升一位路径就变,写死路径必失配。详见 `process.md` §7.0。
> **序号**:同一「使用场景」下有多份时才加(`按需1` / `按需2`),**只剩一份就不加**——序号的用处是排读取顺序,只有一份时它只会误导。
> **为什么要有**:挑文件时只看得到文件名、看不到任何表格;标签把「哪一层 / 什么时候用」写进文件名本身。
> ⚠️ **改名会改变文件名主干**,触发执行端 §八「主干相同、仅版本号不同」判据失效——归档时须在执行卡里点名两个确切文件、写明大脑裁决,不走机械匹配。

## §4 窗口按线开,弃挂窗即重启

事实源在文件里、不在对话里。窗口卡死 → 弃掉,用 §3 冷启动重开接力,**损失为零**。

**一条线一个窗口,不按组件开窗**:支线窗口按**线**划分(支线-通用 / 支线-理财 / …),该线的组件在同一窗口内**逐个串做**,做完一个接下一个。开窗成本是重读 `SKILL.md` + 本文件 + DS `SKILL.md` 入口,按组件开窗等于每个组件重付一次,属纯浪费。

**什么时候才弃窗**:① 窗口卡死 / 上下文溢出;② 该线的批次整体完结;③ 窗口已被前几轮的错误上下文污染、纠偏成本高于重开。**不因「做完一个组件」退役。**

> 主线-大脑的 1 个窗口同理按线长期沿用。

## §5 支线 → 主线 · 交付包

对偶于 §3.2「带什么文件」——那是开窗时给支线的,这是支线交回主线的。给齐 7 项,主线即可直接写库。填写骨架见 `assets/templates/handoff-package.md`。

1. **组件标识**:全限定名(提案)+ Figma node-id + 文件 key + **归属提案**(≥2 场景 → 通用、单一 → 业务、拿不准标问;出处 `SKILL.md` §2 总则7)。
2. **效果确认凭证**:用户确认原话 + **参考实现源 HTML**(去批注即可转参考实现;须 `check-page.py` 0 P0 + 渲染眼检过;`process.md` §4.8 闸B / §5.2)。
3. **直读真值清单**:每个数值 / 颜色给【**变量绑定名 + 解析 hex**】两者;读不到标 ⚠️ 不推导;**绑定名与 hex 不一致时显式标出、不替主线拍 token 名**(语义 token 按用途由主线定:图标 CI / 文本 CT / 涨跌 CS;`process.md` §4.1#1-2)。
4. **构成与嵌套**(复合组件必给):列出内部可复用原子,逐个声明「建议独立成组件 / 折进组合」,指出是否复用既有组件;**不得把可复用原子写死折进组合**(`process.md` §5.1)。
5. **多版草案全带**:同一组件有多版确认草案(如固定宽 vs 自适应)时全带 + 标哪版为准;说明本批交哪些、其余挂哪。
6. **裁决点清单**:凡覆盖直读、用户拍板、缺态补全、命名 / 归属提案,逐条列「🚧 请主线复核 + 依据」(`SKILL.md` §2 总则4)。
7. **未完成同步清单**:待主线做的(写库 / 升版 / Design / 对账 / 发布)分类列出。

**交回位置**:有本地访问的支线写进 `drafts/{支线}/{组件编号}-{组件名}_{日期}/`;无本地访问的由用户上传给主线-大脑。

## §6 撞车(开多支线前)

- **按「互不共享底层」分组件**:两支线别同时改会写同一 token、或同一被嵌套底层组件(按钮 / 图标 / tab / 胶囊 / 分割线…)的东西。
- **真撞了不在支线解决**:各标 ⚠️,交主线合并时裁(`SKILL.md` §2 总则2 **分两层**:涉及设计真值的以 **Figma** 为准,涉及站的以 **skill** 为准)。
- **主线合并顺序**:先并不冲突的,冲突集中裁完再并,**统一签一次版**。

## §8 防漂移

- 本文件是**分工映射 + 开窗专用件**,不放过程规则。改规则去改 `process.md`,不改这里。
- **别再派生新文件装规则**:新规则按归属进用户个人使用习惯文件(通用,如有)、`process.md`(项目过程)或 `execution-standard.md`(执行纪律)。**通用层若不在本项目掌控内(如挂载 skill),规则仍按项目层就近收进 `process.md`,不为它派生新文件。**
- **同一条规则只写一处**:并入前的《主线支线分工卡》与《协同文件包开窗指引》都栽过——分工卡 v1.0 重抄工作流正文成了第二处副本,分工卡与开窗指引又各存一套开场白。**发现某条在两处都写,就该合并或改成指向。**
- **模板只存 `assets/templates/` 一处**:正文引用模板一律给路径,不在正文里再抄一遍(例外:`execution-standard.md` 要单独 cp 给执行端,其反馈模板必须内嵌自包含,见该文件 §五)。
- **对外分发**:直接打包本 skill 包,按对象手动删不该给的——**给同事时删《项目总览》**(含待办、踩坑、否决,对外无意义且暴露内部判断);只要执行端纪律的,给 `references/execution-standard.md` 一份即可。**不另立分发清单**(同一份文件存两处必漂移)。
- **⚠️ 拆条 / 改标题时,先把限定词单独摘出来**:「全员」「一律」「所有」「凡…」看着像修饰语,实际是**这条规则管多宽的唯一依据**。删掉不报错、不冲突,只会让某个角色以为「这条不管我」。
  > **验法**:拆完问一句「**谁必须守这条?**」——答不上来就是限定词丢了。
  > 实证:合包时一次丢了三条(总则3.2「贯穿全员」· 总则6「凡转交给 Design/trae」未扩到主线-手 · 总则7「全员引用组件时遵守」),规则内容都在,适用范围全没了。详见 `CHANGELOG.md` v6.1 §3。
- **⚠️ 新增角色 / 通道 / 载体时,回头扫一遍按旧角色集写死的枚举句**(「发给 X 的…」「X 负责…」)。这类洞不报错,只让新角色在规则里查无此条。
- **改包或改《项目总览》,收尾跑一遍副本扫描**:拿活动件的每个段落去包全文里比对,两处都有规则正文 = 第二处副本,按测试2(`process.md` §7.1)判归属。**不跑这一步,副本只会越攒越多**——本包合并当天就攒出 4 处。
- **新增一处长期存放点前,先问「这条内容多久变一次」**——频率不同的东西不进同一个载体(`process.md` §7.0)。
- **⚠️ 升版之后,已经开着的窗口不会自己知道**。签发方 present 新包时,**同轮附一段「转告各活窗口」的复制框**(总则6 的延伸)。
