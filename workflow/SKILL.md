# 国金DS · 设计系统制作工作流 · WF v6.9

> **本包讲什么**:维护「国金证券客户端设计系统 skill」的**过程规则**——这件事怎么干、谁在哪个窗口干、文件放哪、执行端怎么动手。
> **不讲什么**:设计系统的真值(token / 组件 / 场景)。那是**操作对象**,在 DS skill 里,经其 `SKILL.md` 路由按需读。
> **不发给谁**:不打包进设计系统 skill、不发给原型制作者。

> **文档分层**:本包是**项目层**,与用户个人使用习惯文件(通用层·跨项目·独立版本线,如有)配套。
> **冲突优先级**:**用户当轮明确指令 > 工作流包 > 个人使用习惯文件**。
> 「工作流包」指本包全部内容——`SKILL.md` 与各 `references/` **同一档**,包内不再分档。包内若出现互相矛盾的写法,按 §1 总则0 裁断,并报回修订,不靠档位压制。
> 本包**自包含**,不引用通用层条号(通用层不在本项目掌控内,其版本与章节号随时可能变);少量重叠属合理冗余,不据此删条。
> **新规则归属**:换项目仍成立且通用层可改 → 通用层;否则一律就近收进本包。**不为任何新规则派生包外新文件。**

> **本包版本线**:自 WF v6.0 起统一为**一条**。v6.0 之前是四条独立版本线(制作工作流 / 多窗口协同 / 工作区结构 / 执行端作业规范),旧编号仅供回溯,见 `CHANGELOG.md`「附、并入前的四条版本线」。正文与踩坑记录里出现的 `v1.4`、`v1.10` 等指的是那些线上的编号。

## §1 总则0 · 冲突裁断与优先级

规则冲突时按此裁——

- **① 质量底线不可降级**:事实源唯一(总则1)、两次确认(总则4)、只用 Figma 直读真值不猜(`process.md` §4.1)、版本贯穿(总则3)、影响自升级机制的改动必经用户重点确认(`process.md` §4.6),**不因用户催促或赶进度而跳过**。
- **② 节奏 / 产物选择听用户当轮**:"出不出校验图、发不发某复制框、走 inline 还是 HTML、先做哪个组件"这类**默认动作**,以用户当轮明确指令为准。本包的默认动作是"无人指示时怎么做",**不是用来拦住用户**。
- **③ 二者冲突**:底线优先于催促;不破底线的前提下,用户明确指令优先于本包的默认动作。

> **统一标注符号(全产出适用)**:🚧=需用户确认 · ⚠️=有问题/偏差 · 📋=短期待办 · 🗂️=长期待办 · 📎=附件/随附内容。

## §2 七律(全员、全程适用)

### 总则1 · 设计真值在 Figma;DS skill 是固化而来的 AI 执行载体

**设计真值的唯一来源是 Figma**(本项目指定:**《佣金宝组件库 V2.0》**)。**DS skill 不是设计真值的源头**,它是把 Figma 的真值**固化成 AI 可执行形式**的载体——除了数值,还装着专为 AI 生成写的规则(场景、限制、组合约束)。

**改动顺序:Figma → skill → 站。绝不反向**——「反向」指 **站 → skill** 与 **skill → Figma** 这两个方向,一律不走。

- **skill 有、Figma 没有的内容:正常,保留在 skill。** 那是为 AI 生成补的规则,比 Figma 多属预期,**不算冲突,不必等 Figma 补**。「以 Figma 为准」**只管两边都有、且数值或样式不一致的情况**。
- **Figma 自身前后不一致**(同一组件在不同页面数值不同):**报给用户,由用户决定**。AI **不自行择一**;定了再改 Figma 或改 skill。

**事实源在文件、不在对话**——这条不变,同样适用于本包:窗口卡死就弃掉重开,损失为零(`multi-window.md` §4)。

> **2026-10-23 改口径**:原文是「唯一事实源在设计系统 skill」。用户原话——「经过一段时间的与研发的联调,AI 与 Figma 的畅通程度越来越高,决定最终都以 Figma 的内容为准」。**旧措辞在全包多处出现过,本版已逐处改写**(本页 §3.1 与 §3.4;`process.md` §4.1 与 §4.3;`multi-window.md` §1 与 §6;`workspace.md` 的目录树注释)。

### 总则2 · 差异分两层裁决

| 不一致发生在 | 以谁为准 | 改谁 |
|---|---|---|
| **Figma ↔ skill** | **Figma** | 改 skill(总则1) |
| **skill ↔ 站(Design)** | **skill** | 改站 |

skill 对站而言是**上游**,不是「设计真值的源头」——两件事别混。对账发现站与 skill 不一致,默认 skill 对、Design 改;除非用户指出 skill 该改,才回头走「Figma → skill」那一层。

### 总则3 · 版本与命名

**3.1 版本签发**
CHANGELOG 用语义化 `主.次.修`,是唯一签发源。档位判定按优先级:**① 破坏性变更(最高):token 值、基准、取用顺序等影响既有产物兼容性的 → 主版本位;② 结构性重构 → 主版本位;③ 新增组件/章节 → 次版本位;④ 改细节/勘误 → 修订位**。
设计系统与本工作流版本号**各自独立签发**;**跨资产引用一律带前缀**(DS=设计系统 / WF=工作流,如 `DS v3.29.7`、`WF v6.9`;**各资产当前版本真值一律查《项目总览》§二**,本行只示范写法)。

> **⛔ 签发之后,包的归宿是 Project 文件,不是 `meta/`。**
> present 只是给到用户;**包要能被下一个窗口读到,得进 Project 文件**。
> **⚠️ 这一步只有用户能做**——Project 文档存不了二进制,签发方传不上去。所以 **present 包的同一轮,必须明写一句请用户把它传进 Project 文件并替换旧版**;漏了这句,下一个窗口拿到的还是旧包。`meta/` 里那份是给有本地访问的窗口用的**副本**,按 `process.md` §7.2 同口径**按需同步**——没人要读本地那份时,它旧着不影响任何人。
> **因此:出包**不**默认配一张执行卡。** 只有当本轮确实要动**本地工作区**(归档旧目录、同步执行端挂载副本、整理 `历史文件/`)时才出卡;只换包不动工作区的,**进 Project 就算到位**。
> **实证**:WF v6.7、v6.8 连续两版签发后**都没落地**——执行卡没发,包只到下载夹,Project 文件停在 v6.6,两版就此蒸发,改动要重做。**根因是签发后没有持久归宿,而不是谁忘了发卡。**

> **⛔「签发」以 present 为界,不以落地为界**:包一经交给用户(present / 发出),**该版本号即冻结**;此后任何内容改动——哪怕只改一个字、哪怕用户还没下载、哪怕还没进 `meta/`——都必须**升位重发**,不得沿用同一版本号。
> **理由**:发出去的那一刻你就失去控制了——用户可能已下载、执行端可能已解压、它可能已进 `meta/`。版本号的唯一用处就是在这种时候分辨"这是哪一份",而"还没落地所以不算数"恰恰在最需要它的时候把它冻住。
> **同族**:与「执行卡一经 present 即视为定稿,要改就换卡号重发」是同一条(见 `assets/templates/exec-card.md` §二)。
> **配套 · 每次 present 包必须给出「包内容指纹」**(算法见下),**zip 的字节数与 MD5 同时给,但只作辅助**;**签发当轮同时登记进《DS 改动核验台账》**(`process.md` §7.4)——指纹算得出来、却从包里推不出来,不登记就没人能回头确认手上是哪一份。
> **⛔ 权威钉在内容上,不钉在压缩容器上。** zip 是信封:用户的系统把它自动解开再压回去(macOS Safari 下载后自动展开 + Finder 重新 Compress,会塞进 `__MACOSX/._*`),**内容一字未改而容器 MD5 全变**。拿容器值当权威,下游会把一个完全正确的包判成「不命中」而整卡停下——**白跑一轮,且错的是判据不是包**。
> **实证**:WF v6.5 present 后,用户手上出现 91663 / `0ff7f885…` 的同内容副本(签发件为 83728 / `9ccd640a…`),包内 `SKILL.md` 与 `execution-standard.md` 的 MD5 两份完全一致。
> 本条源于 WF v6.1,v6.6 把权威从容器改到内容,详见 `CHANGELOG.md`。

#### 包内容指纹 —— 算法(照抄,别自创)

对**解压后的包顶层目录**:

1. 列出其下全部普通文件的**相对路径**(相对该顶层目录),**排除系统文件**(`.DS_Store`、`._*`、`__MACOSX/` 下的一切);
2. 用 `LC_ALL=C` 排序;
3. 每个文件输出一行 `{相对路径}` + 两个空格 + `{该文件 MD5}`;
4. 把这份清单文本(含每行末尾换行)整体取 MD5,**即为包内容指纹**。

```bash
# 在包顶层目录内执行。macOS 用 md5 -q,Linux 用 md5sum。
find . -type f ! -name '.DS_Store' ! -name '._*' ! -path './__MACOSX/*' \
  | sed 's|^\./||' | LC_ALL=C sort \
  | while IFS= read -r f; do echo "$f  $(md5 -q "$f" 2>/dev/null || md5sum "$f" | cut -d' ' -f1)"; done \
  | tee /tmp/wf-manifest.txt | (md5 -q 2>/dev/null || md5sum | cut -d' ' -f1)
```

> 中间那份 `wf-manifest.txt` 本身就是诊断件:指纹不符时,**直接 diff 两份清单就知道是哪个文件不同**,不必逐个猜。

**3.2 每份输出物带版本号 —— 贯穿全员每一次输出物**
版本号由 skill 的 CHANGELOG 统一签发(3.1),**全员每一次输出物都要带**,不分角色、不分轮次:
Chat / Code 交付的每个文件(zip/md/css/html)文件名含版本号;每条 Design 提示词开头注版本号;Design 页面内每块内容标其对应版本号(照抄不自创),导出文件名带版本号。

> **⛔ 预览 / 草稿用轮次号 `r{n}`,不带资产版本号。** 轮次与版本号是**两套计数**。
> **判据**:这件东西**签发了吗**?签发了 → 版本号;还在等确认 → `r1`、`r2`…,文件名和标题都不带资产版本号。
> **实证**:骨架图前 3 轮预览内容各不相同、全标「v4.1.0」,用户问「版本号为什么没有迭代」。
> **同族**:与 v6.0「同一个版本号 present 了 5 次」是同一个病——**一个编号背了两种含义**。

**3.3 skill 包命名与上传合规 —— 三条硬约束(红线,违则传不上去、返工)**
1. **顶层目录名 + 全部内部文件 / 目录名一律纯 ASCII**(字母 / 数字 / `_` / `-`,无中文、无点号、无空格)。
2. **版本号存于 `VERSION` 文件 + `SKILL.md` 的 `metadata.version` + `CHANGELOG`**,**不作 frontmatter 顶层字段**。
3. **`SKILL.md` frontmatter 仅用合规字段**:`name`(kebab-case 纯小写)、`description`(触发词并入其末尾)、`metadata`(version / slug / maturity 等自定义字段收纳此处;**不放 baseline 之类的他方版本号**——版本真值只记《项目总览》§二一处,写进这里必过期。实证:本字段曾停在 `DS v3.29.7` 不动,而 DS 已到 v4.1.1)、及 license / allowed-tools / compatibility。`slug` / `version` / `maturity` / `triggers` 等**禁作 frontmatter 顶层字段**(否则 invalid_request_error)。

> 打包细则(目录名带版本的写法、`__MACOSX` 排除、validate.py 守卫、与自升级的关系)见 `process.md` 总则3.3-细则。

**3.4 设计系统 skill 双版交付(按需)**
**默认只出多文件路由版 zip**(主力·全面:三层架构基础规范 / 通用组件 / 业务场景,按 SKILL.md 路由);**单文件·基础规范精简版 `.md` 按需出**——仅当用户明确要分发 / 嵌入底座时再出(只含基础规范真值,文件头注范围并指向全面版)。需要时与 zip 同版本号;基础规范变动后若用户要单文件则同步内容。

**3.5 / 3.6**:站点(展示站)版本号规则、可视化站部署交付规范 → 见 `process.md` 总则3.5 / 总则3.6。它们是**阶段性动作**(打包、上线时才用),不是每轮动作,故不占本页。

> **目的**:任何产出物从 **VERSION / zip 文件名 / CHANGELOG** 即可溯源版本;且 skill 包随时可直接上传 Claude.ai Skill,**不因命名返工**。

### 总则4 · 用户确认才算完成 · 两次确认,Chat 不自行宣布完成

每个组件 / 维度必走两次确认——
- **效果确认(数值与效果)**:过了才写进 skill;
- **文本确认(表述与归属,可抽查)**:过了才打包 / 升 SKILL 版本 / 回写看板 ✅。

待确认清单的拍板(规则、命名、缺态)是**确认前置**,**不替代**两次确认。渲染出图后只能说"请确认效果";用户表态前不得写"已完成"、不标 ✅、**不打包、不升版本、不动看板**、不跳下一步。

- **确认反馈三类**:① 确认通过 → 进下一步;② 指出问题 → 回该次确认改后重看;③ 缩范围 / 延期 → 更新本轮范围后继续。
- **⛔ 修改指令 ≠ 确认。** 「按你推荐的改」「照这个来」是**针对改之前的计划**下的指令;确认**针对改之后的结果**。**出包前要有一次针对「本版实际改了什么」的表态**,修订位也至少要一句。
  > **实证**:DS v4.0.2 在「按你推荐的改」之后直接打包签发,用户没见过改动清单,也没给内容指纹。
- **轻量修订路径**:修订位(仅个别数值 / 措辞小改)走轻量——**只给文案确认、不出校验图**(除非用户要可视化);新增组件 / 章节仍走完整两次确认。

> **两次确认按线分布**:效果确认在支线(过了草案才成立),文本确认在主线-大脑(过了才升版打包)——见 `multi-window.md` §1。

### 总则5 · 任务清单制(每轮必做)

用户每发一条消息,Chat 必须——开头把消息拆为编号任务(含隐含任务,如"修改后需同步 skill");交付前对照逐项核对;结尾每项标 ✅完成 / ⏳进行中(说明卡在哪)/ ❌未做(说明原因),**不静默丢弃任何一项**。单任务轮可精简为开头一行任务 + 结尾一行状态。

### 总则6 · 凡要用户转交给下游的东西,一律配复制框

**适用于所有下游,不限于某一个**:【主线-手】、Design、支线窗口、备用 trae —— 只要**需要用户手动粘贴出去**,就得给复制框。

- 放入**复制框(代码块)整体输出**,便于一键复制;框内为**纯提示词正文**,不混入对用户的说明;说明写在框外。
- **⛔ 交付件 ≠ 提示词,两者都要给**:出了执行卡 md、参考实现文件、草案包,**不等于**完成交付——用户还需要一段话把它转交出去。**产出物与转交复制框必须同轮一起给**,不能只给文件让用户自己组织措辞。
- **各下游的复制框骨架在 `assets/templates/`**:执行卡 → `exec-card.md` §二;开场白 → `kickoff-brain.md` / `kickoff-branch.md`;Design → `design-prompt.md`。**照抄,不自创。**

> **本条适用范围曾漏扩**:原文只写「Design(或备用 trae)」,写于【主线-手】这个角色存在之前;v5.7 新增执行端时没回头扩这条,导致「发执行卡要不要连带给复制框」在规则里无处可查,实战中连续漏发。**新增角色 / 通道时,须回头扫一遍所有按旧角色集写死的条款**(同族坑见《项目总览》§五)。

### 总则7 · 组件全限定命名

**全员引用组件时遵守**——大脑、支线、手、Design 一律适用,不分窗口。

- 语法 `族 - 形态 - 档位 - 排布`,状态(选中 / 未选)按需作尾缀;**档位主键 = Figma 变体属性值**(尺寸=M/S/XS/60/80/100、层级=一级/二级等),名称须能在源文件锚定到真实变体,**禁用推导值(高度 / 宽度)当主键**;规格仅作括号附注(如 tab-胶囊-XS(高44·字24))。
- **禁止裸档位**:不得脱离族与形态单说「80档」「XS」「M」;跨章节 / 跨协作方引用至少写到「族-形态-档位」。
- **变体值优先于场景**:Figma 变体值本身是层级词(一级 / 二级)则如实入名;名称不附加变体之外的使用场景(场景写在规格表「适用场景」列)。
- **排布受控词表**:仅「左固 / 等分 / 通栏」三词;其余写法废除。
- **曾用名登记**:改名组件在 skill 保留「新名↔曾用名」对照表,仅供回溯;新表述一律用新名。
- **业务组件场景前缀**:三层架构(基础规范 / 通用组件 / 业务场景);业务组件全限定名带场景前缀「{场景}/族-形态-档位」(如 基础/AI智能体/导航栏-对话)。场景受控词 = **8 业务域(与 skill 三层架构对齐):基础 / 账户 / 增值 / 行情 / 交易 / 理财 / 资讯 / 端外**(基础、端外含子域,用二级前缀,如 基础/AI智能体、端外/微信小程序);调整须用户拍板。
- **归属判定**:**≥2 个场景使用 → 通用组件;仅单一场景 → 业务组件(对应 `scenarios/` 文件);拿不准 → 问用户**。场景文件对全局的差异属合法覆盖,对账时先查场景层再查通用层。
- **命名是规则,归 Chat 提案、用户拍板**:新组件 / 档位命名先按本语法提案、经确认后随固化入库;Chat 直读 Figma 原始变体值,与规范名天然对齐。

## §3 角色与通道

### 3.1 四方分工

- **Chat(大脑 / 固化与裁决)**:判断、取舍、结构设计、措辞;把 Figma 直读来的"样式数值"赋予语义与规则、固化进 skill;校验与裁决。**它维护的是 skill 这个执行载体,不是设计真值本身**(总则1)。
- **Code(工厂 / 校验器,在 Chat 内调用)**:确定性批量活——抽取 token、零误差生成 css/md、一致性校验、渲染校验图、与设计图叠加比对、打包。
- **主线-手(执行端,Chat 外的独立窗口)**:承担上述「Code」槽位的确定性活——文件建 / 移 / 改名 / 解压 / 打包 / 归档、跑校验脚本、机械检查支线草案。**只执行主线-大脑已下达的指令,不做业务裁决、不自行判断版本升位。** 作业纪律见 `references/execution-standard.md`(挂载给执行端常驻),本页不重抄。
- **Figma 读取(Chat 经 MCP 直读)**:Chat 经 Figma 官方 MCP 直读节点结构(`get_metadata`)、设计上下文(`get_design_context`)、变量 / 语义 token 绑定(`get_variable_defs`)。直读值即实测值,且能拿到变量语义 token 绑定(免去 hex 撞库猜测)。
  > 备用:外部提取模型(trae)是 MCP 不可用时的回退;启用时仍守「仅提数值、不碰规则语义、推导拒收」。
- **Design(橱窗 / 可视化)**:把定稿内容画成对外展示的精美可视化页。

一句话:**设计真值在 Figma;Chat 直读 Figma 并把它固化成 skill,规则与裁决在 Chat(主线-大脑);文件执行交主线-手;Design 只做对外橱窗。skill 是站的上游,不是 Figma 的上游。**

> 各角色的载体、开窗方式、边界与交回物 → `multi-window.md` §1–§3。

### 3.2 轮次编号制 —— 窗口码 + 各自独立序列

凡有下游执行者的任务,**每轮签发一个唯一编号**,下游一切产出物(执行反馈、草案、交付件)的文件名与标题都带该编号。

#### 编号格式

```
EXEC-{窗口码}-{三位序号}          例:EXEC-WF-001、EXEC-DS-014
```

- **窗口码绑「任务域」,不绑「窗口实例」。** 窗口卡死重开、换人接手,码不变、序列接着走(`multi-window.md` §4 窗口可弃)。
- **每个任务域一条独立序列,各自从 `001` 起。** 域与域之间**不共享计数器**——共享计数器要「读—改—写」,两个窗口同轮各读到同一个值就都会用它,**撞号是必然不是偶然**。
- **码的分配与各域当前最大号登记在《项目总览》§三**。那是**登记表不是锁**:即使某窗口记错,错也只在本域内,且一眼可见。

> **⛔ 为什么不用共享计数器**:v6.4 试过「下一个可用编号记在《项目总览》」,**在多窗口下不成立**——各窗口拿到的《项目总览》是用户当轮上传的快照,彼此看不见对方的写入。**结构上不可能相撞,才叫防撞;靠协调不撞,只是还没撞。**

#### 三条配套

- **编号与载体无关**:正式执行卡是它,直接贴一行短清单也是它,共用本域那条序列。**不设「短任务免编号」的例外**——一有例外,下游就得先判断再选格式,那个判断点就是下次出错的地方。
- **漏发编号是出卡方的失误**:下游标 ⚠️ 报回并沿用上轮编号加 `-b`,**不因此降级输出形态**。
- **收卡端撞号即拒收**:编号与已执行过的某轮重复时,执行端停下报回、不执行(`execution-standard.md` §九)。**这是最后一道网**——只有执行端同时见过所有窗口的卡。

#### 文件名

`{编号}-{任务摘要}.md`,例 `EXEC-WF-001-land-v6-5.md`。

- **摘要必须含「对象」,不能只有通用动词。** ❌ `land-package` / `update-doc`(哪个包?哪份文档?)✅ `land-v6-5` / `fix-listheader-p1`。**不同窗口的通用动词必然重名**,而编号已经防住了撞号,摘要要防的是**人眼认错**。
- **⛔ 文件名里不写版本号之外的版本信息**——版本号写进卡的正文;摘要里那个 `v6-5` 是**对象名的一部分**,指的是「哪件东西」,不是「本卡属于哪版规则」。
- 执行卡不进工作区、不打包上传,**不受总则3.3 的 ASCII 命名约束**。
- **编号在 present 那一刻才取,起草时不占号。** 实证:`EXEC-DS-002` 作废、`003` / `004` 未发即废——**五个号里三个空转**。
- **下游产出物的命名**以其常驻规范为准(`execution-standard.md` §五),本处不重抄。

> 执行卡骨架 → `assets/templates/exec-card.md`。
> ⛔ **出执行卡时必须同轮附上转交复制框**(总则6),只给 md 不算交付完——骨架在该模板 §二。

### 3.3 文件连通性(硬约束)

三方之间没有直连,但已有**本地工作区**作为共同落点:有本地访问能力的窗口(主线-手、授权了文件夹的支线)直接读写工作区。目录结构与权限矩阵见 `workspace.md`。

> **⛔ 通道由载体能力决定,底线不随载体变。**
> 主线窗口的载体**若没有**文件读写能力,文件操作经主线-手执行或由用户上传 / 下载;**若有**(能解包、改文件、跑校验脚本、打包),**确定性操作自己做,不出执行卡**——为一次机械操作走一轮执行卡是纯浪费。
> **但执行卡带来的三件事一件都不能少**:① **不可逆操作先声明确切目标**;② **留证**——改了哪些文件、验证结果当轮写清,不只报「已完成」;③ **签发纪律照旧**(总则3.1 给指纹、总则4 确认后才打包、当轮登记《DS 改动核验台账》)。
> **⚠️ 能力也可能比你以为的少**:某些载体能读写**自己的工作区**却够不到**用户本地工作区**。动手前先确认这一轮要碰的是哪一个,**够不到就如实说、不要假装出卡**。
> **实证**:DS v4.0.2 / v4.0.3 / v4.1.0 / v4.1.1 四版全由主线窗口直接改直接出包,规则里没有这种载体的位置,每轮都要临时判断。
> ⚠️ 原文写死「主线-大脑无本地访问能力」,**是按旧载体事实集写死的枚举句**(同族见 `multi-window.md` §8)。

| 通道 | 通/断 | 走法 |
|---|---|---|
| Figma → Chat(MCP 直读) | 通 | Chat 经连接器直读节点 / 变量,无需中转 |
| Figma → Chat(截图/PDF/SVG/文字) | 通 | 用户导出上传,唯一入口 |
| Chat/Code → 用户(md/css/zip/html) | 通 | present,用户下载 |
| 用户 → Design(提示词) | 通 | 粘贴 |
| Design → Chat(html/zip) | 通 | 用户导出上传,Code 可解析 |
| Code ↔ Figma/Design 直连 | 断 | 无外网,全靠用户中转 |
| 主线-手 ↔ 本地工作区 | 通 | 按授权目录直接读写 |
| 支线(有授权) ↔ 本地工作区 | 通 | 只授权自己那个 `drafts/` + `skill/` 只读 |
| 主线-大脑 ↔ 本地工作区 | **看载体** | 载体无文件能力 → 断,经主线-手执行或用户上传下载;**载体有文件读写能力 → 通,确定性操作自己做,不出执行卡** |

设计目标:**让用户搬运次数最少、每次搬的东西最明确;能交给执行端做的不让用户做。**

### 3.4 全链路总览

从一个组件的「想法」到「线上可访问」,五个阶段:

```
① 构思/取值  —— Chat 经 Figma MCP 直读节点真值与变量绑定(§4.1);源规范不全则 Chat 完善(§4.2)
       │            产物:已读到/⚠️待确认清单 + 命名提案(用户拍板)
② 固化      —— Chat 裁决赋义 → 效果确认过 → 写进 skill(md/css)→ 文本确认过 → Code 校验/打包/升版本
       │            产物:效果确认校验图 → 确认后 DS skill(多文件路由 zip;单文件基础规范按需)
③ 展示      —— 用户把「只含定稿差异」的提示词/参考实现文件给 Design → Design 更新可视化站(§5.4)
       │            产物:多页自包含可视化站(每页内联、离线可预览)
④ 对账取证  —— Design 导出回传 → Chat 先核版本戳 → Code diff + Figma 直读逐项核验(§4.3)→ 偏差回 Design 修
       │            产物:取证通过的可视化站
⑤ 发布/部署 —— 整理 ASCII 文件名部署包(index.html 在最外层 + 英文页 + assets/ + 下载 zip)→ 上线(§4.5)
                    产物:线上站点 + 站内可下载的权威 skill 包
```

铁律贯穿:**设计真值在 Figma、skill 是固化而来的执行载体**(总则1);差异**分两层裁决**——Figma ↔ skill 以 Figma 为准、skill ↔ 站以 skill 为准(总则2);版本号全员贯穿(总则3);用户确认才算完成(总则4)。**展示 / 发布层只动表现与文件名,绝不反向改真值。**

> 上表 §4.x / §5.4 均指 `references/process.md`。

## §5 用户每轮只需的动作

- 发 Figma 节点链接给 Chat(新维度 / 组件;截图作补充);
